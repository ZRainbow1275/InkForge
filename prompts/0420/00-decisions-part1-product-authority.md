## §1 产品哲学总纲（1800 字）

### 1.1 一句话定位

**InkForge v2.1 是 Markdown-first 的单人深度写作与多渠道出版中枢 —— 以纸张式安静写作为气质、以 Typora 风格所见即所得为默认编辑范式、以 Markdown 文本为唯一表达权威、以多平台独立渲染链路为出版契约、以零空壳与全量审计为交付底线的本地优先桌面应用。**

### 1.2 产品三轴与近远期

InkForge 围绕四个典型场景被组织起来：A（单人深度写作）、B（小团队协作）、C（知识增强）、D（多渠道出版）。**本轮主轴是 A + D 双核**（L1-01），把 C 放在近期次轴（知识增强、引用溯源、AI 扩展点均要在本轮预留骨架与垂直切片），把 B 放在远期（评论与审阅基础闭环必须进本轮，但"多人实时协作"、"责任指派与截止时间"等能力推后；L1-14、L1-16）。

目标用户主战场是**个人本地用户**（L1-02）。但"5-10 人团队 + 管理员/非作者角色"是远期锚点，因此多账户、同步、审计、权限四条骨架**必须在本轮真实落地**而不是 UI 占位（L1-02、L1-20、L1-33、L1-34）。这意味着 InkForge v2.1 不引入任何"云端强依赖"作为必需路径，所有能力默认离线可用；同步、发布、AI 等外部集成均为**可选增强层**。

### 1.3 设计哲学：纸张式写作与 iA Writer 传承

InkForge 的气质基石是"纸张式写作"（L1-12）：居中纸张、受控宽度档位、克制的颜色体系、柔和的行距字体基调、安静的写作区。竞品借鉴纯属 A 档位（L1-39）：Typora、iA Writer、MarkText 的方向——**Markdown-first、所见即所得、安静写作**——任何偏 Notion / Obsidian 的块数据库化、关系图谱化倾向在 PRD 阶段必须被明确否决。

但"纸张式安静"不等于"功能匮乏"。v2.1 允许**重度工具栏**与**精致动效**作为可切换模式（L1-12 补充），允许用户在"简化工具栏（默认）/ 完整工具栏"间选择。`L1-49 B+C + L1-50 + L1-52 A`组合表达了用户的核心诉求："功能必须第一天就全部可见，但默认展示必须极简、可随时关闭、不强制引导"。因此本产品采用 **"默认极简，全开关可打开"** 原则：StatusBar 可整体关闭（N-01 补充）、引导仅保留欢迎弹窗（L1-50 补充）、专注模式保留所有功能入口仅隐藏 UI（L1-46 补充）。

视觉一致性是硬门槛（T09-13 D + 补充）——**严禁 emoji，严禁任何与 Ethereal Constructivism 设计语汇不一致的"似是而非"新风格**；任何新组件必须映射到已有设计字典。

### 1.4 编辑范式：Typora 式所见即所得 + 状态全继承

默认编辑范式是 Typora 式混合编辑（L1-10 B）：平时所见即内容，光标进入才暴露语法标记。表格、代码块、公式、Mermaid、图片、Callout 等**重块元素默认走渲染态**（L1-13 B），光标进入切换到源码态。代码高亮、公式、图表在编辑器、预览、导出三端必须**视觉高度一致**（L1-32）。

模式切换（Typora ↔ Source ↔ Preview）时**所有状态必须继承**（L1-11 C + 补充）：选区、撤销栈、版本点、评论锚点、滚动位置、折叠状态都不得中断。这是产品最核心的体验契约之一。

### 1.5 权威哲学：Markdown 是唯一表达权威

**Markdown 文本是内容的唯一表达权威源**（L1-05 A）。渲染、预览、导出、发布、搜索、AI 集成一律从 Markdown 派生，任何平台适配都不得反向污染 Markdown 权威模型（L1-30 + 补充）。这是 InkForge 区别于大多数富文本产品的根本决策。

但由于当前代码事实上以 HTML 作为数据库层持久化事实，本文档确立**"表达权威 vs 运行时持久化权威"双层模型**（裁决 L1-05 vs L1-06）：

- **表达权威 = Markdown**：所有用户意图、所有派生（渲染/导出/索引/AI）、所有版本的"真值来源"
- **运行时持久化权威 = HTML（v2.1 维持现状，X-06）**：IndexedDB 层面的缓存与快速恢复载体
- **一致性契约**：写入路径 `Markdown → HTML 渲染缓存`；读取 / 修改路径必须以 Markdown 作为 source of truth；HTML 缓存损坏时应从 Markdown 重建而非反之

非标准 Markdown 能力参考 Typora 策略（L1-07 C）：允许 InkForge 专属增强语法（高亮、Callout 等），但**必须显式标记"不可移植 / 非标 Markdown"**并在导出为标准 Markdown 时走明确降级路径。Round-trip 门槛被用户补充拉到"所有元素无损"（L1-08 C + 补充），即任何增强语法在 Typora / Source / Preview / Export 四态间必须无损往返。

### 1.6 交付哲学：零空壳 + 全量审计 + 硬性能 SLO + 数据底线

本轮交付刚性要求达到"垂直切片 + 高风险能力自带恢复/校验/错误处理"（L1-04 D + 补充）。**任何进入 scope 的能力都必须是真实可运行的代码**，不得交付空壳 UI；任何 scope 内 Spec 条目都必须有对应的代码、测试、验收证据（X-12 D + 机器测试先行补充）。P0 全部 + 核心 P1 必须在本轮完成（L1-03 B）；不设工期（X-08），以质量作为完成判据。

全范围审计（L1-34 A+B+C + 补充裁决为全范围）：安全、编辑生命周期、审阅权限、AI/命令 **四类全留痕**；保留 3 个月、可导出、用户可查看。防呆达到 C 级（L1-40 C）：删除/恢复/导入/导出/切账户/批量命令一律二次确认或自动备份；高危操作必须配合系统级认证（T06-09 D）。

性能 SLO 是硬指标（L1-36 C + X-05 C）：输入零延迟感知、保存 ≤ 1s、冲突检测 ≤ 10s、导出 ≤ 3min、Lighthouse Performance > 80。规模指标（L1-35）：单文档 90 万字符、附件 2000+、版本 999、账户 50+。

最终底线是 **"文章不能丢"**（X-11 补充）。灾难恢复走 C 档（完整性检查 + 安全模式 + 自动快照恢复），配合 R-01 D 崩溃恢复、R-05 D 数据完整性校验形成三重兜底。

## §2 20 条铁律 R-01 ~ R-20

> 每条铁律都是**可拒绝交付**的硬门槛。PR 若违反任一条，PR reviewer 必须 block。

### R-01 | Markdown 表达权威唯一

- **来源**: L1-05 A + L1-30 D 补充
- **含义**: 渲染、预览、导出、发布、搜索、AI 集成皆从 Markdown 源派生；任何平台适配器不得反向改写 Markdown 权威模型。
- **执行**: 数据链路审查；所有 exporter 签名必须是 `(markdown: string) → platformArtifact`，禁止 `(html: string) → …`。

### R-02 | 所有元素无损 round-trip

- **来源**: L1-08 C + 补充"所有元素必须无损"
- **含义**: 任何标准或增强 Markdown 语法在 Typora / Source / Preview / Export 四态往返中必须无损。
- **执行**: 为 19 种元素（T01-15 A）+ 增强语法（高亮、Callout-推后、脚注、details、TOC、Math、Mermaid）构建 round-trip fuzz 测试。

### R-03 | 零空壳交付

- **来源**: L1-04 D + 补充
- **含义**: Spec 中出现的能力必须有真实可运行代码；高风险能力必须自带恢复/校验/错误处理链路。
- **执行**: 每个 Task PR 必须带 X-12 D 验收证据（机器测试 + 截图 + 日志 + 对比样本）。

### R-04 | 纸张式视觉基调冻结

- **来源**: L1-12 B + 补充
- **含义**: 视觉、颜色、行距、字体基调冻结；允许重度工具栏和动效作为可切换模式，但不得破坏基底写作感。
- **执行**: 设计语汇字典 `design-language.md` + code review 反例清单（尤其禁 emoji、禁后台表格感）。

### R-05 | Typora 模式状态全继承

- **来源**: L1-11 C + 补充"所有状态必须继承"
- **含义**: Typora ↔ Source ↔ Preview 切换时，选区、撤销栈、版本点、评论锚点、滚动位置、折叠状态必须连续。
- **执行**: 模式切换路径必须覆盖集成测试；任何 reset 都需显式注明理由。

### R-06 | 版本恢复走 diff/merge + 状态跟随

- **来源**: L1-18 D + 补充
- **含义**: "恢复版本"不得直接覆盖；必须打开双栏 diff/merge，允许选择性恢复；文档状态（评论锚点、选区、配置）跟随恢复。
- **执行**: Recovery UI 必须是 diff/merge 双栏；对版本包（X-09 D）做完整还原。

### R-07 | 自动保存失败用户可见 + 留日志

- **来源**: L1-19 D + 补充"失败重试一次；需要用户可见性完全；需要日志"
- **含义**: 失败重试一次；不得静默降级；必须写审计日志；提供失败明细与应急导出入口。
- **执行**: autosave pipeline 的失败路径必须 emit 到全局 ErrorCenter + activity_logs。

### R-08 | Sync 三 Provider 真实落地

- **来源**: L1-20 D + 补充"必须落地 WebDAV/Git/自有服务"
- **含义**: v2.1 必须提供 WebDAV / Git / 自有服务 三种 Provider 的可用实现，不得仅留接口 stub。
- **执行**: 对应三个 exporter 集成测试必须通过；Sync Tab 不得出现 "即将推出" 字样。
- **协调**: T07-02 选 D（Git 同步）为 Settings Tab 默认演示形态；但底层 Provider 接口必须支持三者并存。

### R-09 | 冲突解决以用户为主 + 审计留痕

- **来源**: L1-22 D + 补充"一律以用户解决为主"
- **含义**: 冲突默认尝试三方合并，但即使成功也必须让用户确认（UI 始终显示三方结果）；所有冲突解决事件写审计日志。
- **执行**: 冲突 UI 强制确认按钮 + audit event `conflict.resolved`。

### R-10 | 账户 = Profile + 多实例并行

- **来源**: L1-23 D + L1-24 D + 补充
- **含义**: 每账户独立数据库 + 独立文件根；支持多窗口并行打开（类 VSCode New Window）；不强制关闭当前文档。
- **执行**: `profileStorage` 以 profileId 分区；Tauri 多窗口 + 账户隔离集成测试。

### R-11 | 引用与溯源三层强制

- **来源**: L1-26 D + 补充
- **含义**: "原始事实 / 模型推断 / 用户手写"三层必须可区分；引用位置可配；导出保留；发布可隐藏。
- **执行**: 节点类型 `citation.factual | citation.inferred | user.authored` + CSS 标记 + export hook。

### R-12 | 命令系统四类分离 + 统一注册表

- **来源**: L1-27 D + T05-09 D + 补充"区分编辑命令/系统命令/AI 命令/发布命令"
- **含义**: 四大类命令各自独立 namespace、独立权限策略；统一注册表承担权限、审计、回滚、搜索排序。
- **执行**: `commandRegistry.ts` + 命令类型枚举；四类命令的权限矩阵见域 H（Part 2）。

### R-13 | 平台独立渲染链路 + 不反向污染

- **来源**: L1-30 D + 补充"各平台独立"
- **含义**: Markdown 权威源共享；从 Markdown 到平台产物的渲染管道各自独立；适配器不得反向修改 Markdown 权威模型。
- **执行**: exporter 目录 per-platform；禁止 exporter 之间互调；禁止 exporter 修改 DB 层文章正文。

### R-14 | 公式/Mermaid/代码高亮 三端一致 + 降级规则

- **来源**: L1-32 C + 补充
- **含义**: 编辑、预览、导出三态在语义与视觉上高度一致；必须为每平台定义降级规则（源码保留 / 占位 / 图像回退）。
- **执行**: 每 exporter 的 `fallback.ts` 必须覆盖三类渲染失败场景；禁止 "编辑器可用但导出坏" 的隐形降级。

### R-15 | 性能 SLO 硬指标

- **来源**: L1-36 C + X-05 C + 补充
- **含义**: 输入零延迟、保存 ≤ 1s、冲突检测 ≤ 10s、导出 ≤ 3min、Lighthouse Performance > 80。
- **执行**: CI 集成 lighthouse-ci；每 Task 验收包含性能基线对比。

### R-16 | 数据底线 — 文章不能丢

- **来源**: X-11 C + 补充"决不能接受文章消失"
- **含义**: 启动前完整性检查；异常进入安全模式；自动恢复最近快照；任何降级路径不得触及正文内容（S-15 补充）。
- **执行**: `DataIntegrity` Spec + `CrashRecovery` Spec + `SafeMode` 启动参数三者联合兜底。

### R-17 | 全范围审计 + 3 个月保留

- **来源**: L1-34 A+B+C + 补充裁决为 D（全范围）
- **含义**: 安全、编辑生命周期、审阅权限、AI/命令 四类全留痕；保留 3 个月；可导出；用户可查看。
- **执行**: `activity_logs` schema 必须包含四类 event kind；Settings > Data Tab 必须可导出并可视化。

### R-18 | 高危操作二次认证 + 自动备份

- **来源**: L1-40 C + T06-09 D + 补充
- **含义**: 删除/恢复/导入/导出/切账户/批量命令 + 删文章/删账户/敏感设置/全量导出等高危动作必须二次确认或系统级认证；并自动生成版本点或备份。
- **执行**: 高危命令清单维护在 `command-registry` 的 `requiresAuth` / `createsVersionPoint` 字段。

### R-19 | 开放扩展 + 沙箱防作恶

- **来源**: L1-37 D + L1-38 C + 补充"完全开源，全部开放"
- **含义**: 完整插件 SDK（生命周期、权限、事件、UI 注入点）；扩展必须声明权限并受沙箱限制；集成定位"服务于写作"，不作通用平台。
- **执行**: SDK Spec（Part 2 域 M）+ 扩展签名声明 + 运行时健康检查（R-04 D）。

### R-20 | 验收证据机器优先 + 矩阵齐全

- **来源**: X-12 D + 补充"机器测试在先"
- **含义**: 每 Task 必须有 Vitest + Playwright E2E 双层机器测试通过；附截图、日志、导出产物、对比样本；涵盖正向/失败/恢复/边界四类样本。
- **执行**: `acceptance-matrix.md` + `artifacts/<task-id>/` 目录强制规范。

## §3 域 A | 产品边界与交付形态

### 决策 A-01 | 产品第一性目标 = A + D 双核

- **规范化结论**: 本轮**主轴 = A（单人深度写作）+ D（多渠道出版）**；次轴 = C（知识增强，预留骨架与垂直切片）；远期 = B（评论/审阅只做基础闭环，协作推后）。
- **硬约束**: 任何 Task 的 P0 内容必须围绕 A/D 锚定；B/C 能力在本轮为"骨架 + 关键垂直切片"而非完整实现。
- **落地点**: Part 3 Roadmap + 所有 Task Spec 的优先级表。

### 决策 A-02 | 用户 = 个人本地优先 + 5-10 人远期锚点

- **来源**: L1-02 A + 补充
- **规范化结论**: 主战场 = 个人本地用户；但多账户（≥ 50）、管理员/非作者角色、同步、审计、权限**骨架必须预留**供远期 5-10 人团队扩展使用。
- **硬约束**: v2.1 **不得引入任何云端强依赖**作为必需路径。
- **落地点**: `T06 账户系统`、`T07 Settings`、`T02 Hub`、`X-04 迁移`。

## §4 域 B | Markdown 权威模型与渲染契约

### 决策 B-01 | Markdown 表达权威唯一

- **来源**: L1-05 A + 补充"核心是 html+css 渲染 + 便于 AI 集成"
- **规范化结论**: Markdown 文本 = 内容的**唯一表达权威**。所有派生（HTML / PDF / 发布 / 搜索索引 / AI 输入）均从 Markdown 派生。
- **硬约束**: 任何模块**不得以 HTML、JSON、平台产物作为 source of truth**。
- **落地点**: `src/services/markdown-authority/`、Exporter 签名规范。

### 决策 B-02 | HTML = 运行时持久化缓存（二元模型）

- **来源**: L1-06 D + X-06 B + 补充"参考微信/小红书编辑器"
- **规范化结论**: 定义**"表达权威 / 运行时持久化权威"二元模型**：
  - **表达权威**（Markdown）：用户意图的真值来源；所有派生起点；版本快照对象
  - **运行时持久化权威**（HTML）：IndexedDB 层面的缓存；用于快速加载与 round-trip 加速；**不是真值**
- **一致性契约**:
  - 写入：`用户编辑 → TipTap JSON → Markdown 序列化（权威）→ HTML 渲染缓存`
  - 读取：`优先从 Markdown 反序列化；HTML 缓存仅用于验证/加速`
  - 损坏恢复：`HTML 缓存损坏时从 Markdown 重建；Markdown 损坏时从版本历史恢复`
- **硬约束**: HTML 缓存字段在 DB 中带 `cacheVersion` 与 `sourceHash`，hash 不匹配时必须 invalidate。
- **落地点**: `src/db/schema.ts`（articles 表新增 `markdownSource`、`htmlCache`、`sourceHash`）；`src/services/content-sync/` 负责双向同步。

### 决策 B-03 | 非标 Markdown 能力 = Typora 策略 + 显式移植性标记

- **来源**: L1-07 C + 补充"参考 typora 策略"
- **规范化结论**: 允许 InkForge 专属增强语法（高亮 `==…==`、Callout-推后、details、脚注、TOC、Math 扩展语法）；每种增强语法在**导出为标准 Markdown 时必须带可移植性标记**（注释标签或 sidecar 元数据）。
- **硬约束**: 导出为标准 Markdown 时，不可移植的部分必须提供降级预案（fallback 文本 / 占位注释）。
- **落地点**: `src/services/markdown-ext/` 每个扩展语法的 `ext-spec.json`（declares portability、fallback）。

### 决策 B-04 | Round-trip 门槛 = 所有元素无损

- **来源**: L1-08 C + 补充"所有元素必须无损"
- **规范化结论**: 19 种标准元素（T01-15 A）+ 所有增强语法（高亮/脚注/details/TOC/Math/Mermaid）必须在 Typora / Source / Preview / Export 四态间无损往返。
- **硬约束**: round-trip fuzz 测试必须 100% 通过；发现不合规立即回滚。
- **落地点**: `tests/roundtrip/` 目录 + CI 强制跑。

### 决策 B-05 | Frontmatter = 双写（YAML in-file + DB 镜像）

- **来源**: L1-09 D + 补充"源文件设置 + 数据库字段管理"
- **规范化结论**:
  - **In-file YAML frontmatter**：Markdown 源文件头部，用户可直接编辑
  - **DB 镜像字段**：IndexedDB articles 表对应字段，支持快速查询与过滤
  - **Source of truth**：**YAML frontmatter 为权威**；DB 字段为派生缓存
  - **导出/发布/搜索映射**：需在 `frontmatter-mapping.json` 中定义每个字段的去向（见 Part 2 域 J）
- **硬约束**: 编辑 YAML 必须立即同步到 DB 镜像；DB 字段不得独立被修改（否则与权威冲突）。
- **落地点**: `src/services/frontmatter/`、`src/db/schema.ts` articles 表。

### 决策 B-06 | 平台渲染链路独立（不共享 pipeline）

- **来源**: L1-30 D + 补充"各平台独立链路"（冲突裁决）
- **规范化结论**:
  - **共享部分**：Markdown 权威源（所有 exporter 的输入）
  - **独立部分**：Markdown → 平台产物的转换管道各自独立
  - **不反向污染**：任何 exporter 不得修改 Markdown 源或 DB 中文章正文
- **硬约束**: exporter 目录按平台划分（`wechat/`、`zhihu/`、`redbook/`、`html/`、`markdown/`、`pdf-deferred/`）；禁止跨目录互调；禁止 exporter 写回 DB。
- **落地点**: `src/services/exporters/*`。

### 决策 B-07 | 视觉保真 vs 平台合规 = 按平台独立策略

- **来源**: L1-31 C + 补充"各平台规则不一，必须独立策略"
- **规范化结论**: 每个平台有独立的"视觉保真 / 平台合规"优先级与预设；至少 5 种预设（微信 / 小红书 / 知乎 / HTML / Markdown）。
- **硬约束**: 每个 exporter 必须声明 `fidelityPriority: 'visual' | 'compliance' | 'semantic'` 与 `fallbackChain`。
- **落地点**: 每 exporter 的 `preset.json`。

### 决策 B-08 | 公式/Mermaid/代码高亮 = 三端一致 + 降级必备

- **来源**: L1-32 C + 补充"微信 CSS/SVG 规则诡异"
- **规范化结论**: 编辑、预览、导出三态必须在语义与视觉上高度一致；为每平台定义降级策略：
  - **源码保留**（最基础）
  - **占位提示**（用户可见降级）
  - **图像回退**（Mermaid → PNG/SVG；公式 → SVG）
- **硬约束**: 禁止 "编辑器可用但导出坏" 隐形降级；任何降级必须对用户可见。
- **落地点**: 每 exporter 的 `fallback.ts`；`T04-spec.md` 降级矩阵。

### 决策 B-09 | 代码块契约 = 语法高亮 + 复制 + 行号 + 折行/横滚（按平台）

- **来源**: T04-13 C + 补充"一切以平台规则为准"
- **规范化结论**: 编辑器内：完整能力（高亮 + 复制 + 行号 + 折行/横滚）；导出态：按平台规则自适应。
- **硬约束**: 编辑器内富文本复制需支持多 MIME（text + HTML + Markdown）。
- **落地点**: `CodeBlock.vue`、`src/editor/clipboard.ts`。

### 决策 B-10 | 渲染资产嵌入 = 按平台规则

- **来源**: T04-14 C + 补充

### 决策 B-11 | 安全沙箱 = 最小清理 + 各平台兜底

- **规范化结论**: 全局只清理明显危险（script / inline-event / javascript: 协议）；细粒度白名单交给各 exporter 自主实现。
- **硬约束**: **全局清理必须包含**：`<script>`、`on*` 内联事件、`javascript:`/`data:` 协议（特例除外）、`<iframe>`（默认禁用，exporter 可 opt-in）。

### 决策 B-12 | KaTeX 完整 WYSIWYG + 红色报错 + 修改自清

## §8 域 F | 同步与冲突

### 决策 F-01 | Sync = v2.1 真实落地 + 三 Provider

- **来源**: L1-20 D + 补充"WebDAV/Git/自有服务必须落地"
- **规范化结论**: v2.1 必须落地：
  - **WebDAV Provider**（完整实现）
  - **Git Provider**（完整实现，作为 Settings Tab 默认演示形态，T07-02 D）
  - **自有服务 Provider**（MVP 级实现）
- **硬约束**: 不是"UI 预留 + 假实现"；Sync Tab 不得出现 "即将推出"。
- **落地点**: `src/services/sync-providers/{webdav,git,inkforge-server}/`。

### 决策 F-02 | 冲突检测粒度 = 架构预留 C 级（行内）但本轮按 D 单写者假设

- **来源**: L1-21 D + 补充"远期必须行内/标记级" → 裁决
- **规范化结论**: **本轮架构按 D 走（单写者假设）** → 单文档同一时间只有一个活跃写者；**但数据结构与算法必须预留 C 级粒度**（行内/标记级），远期升级无需数据迁移。
- **硬约束**: 冲突检测函数签名必须支持粒度参数 `granularity: 'document' | 'block' | 'inline'`，即便当前默认 `document`。
- **落地点**: `src/services/conflict-detect/`。

### 决策 F-03 | 冲突解决 = 三方合并优先 + 用户必确认 + 审计

- **来源**: L1-22 D + 补充"一律以用户解决 + 审计"
- **规范化结论**:
  - 默认尝试三方合并（D）
  - **即使自动合并成功，UI 也要让用户确认**（C 的补充意图）
  - 所有冲突事件写入 activity_logs（R-17）
- **硬约束**: 不允许无声自动合并生效；即便用户点"采纳自动合并结果"也需要显式动作。
- **落地点**: `src/services/conflict-resolve/` + `ConflictResolveDialog.vue`。

### 决策 F-04 | 同步性能 SLO = 冲突检测 ≤ 10s

- **来源**: L1-36 C 补充
- **规范化结论**: 冲突检测必须在 10 秒内完成，否则降级到简化检测 + 提示用户重试。
- **硬约束**: 超时路径不能阻塞用户编辑。
- **落地点**: `conflict-detect` timer + fallback。

### 决策 F-05 | Tauri 文件系统同步 = 外部编辑冲突检测

- **来源**: L1-54 D + 补充"必须支持打开本地 .md 文件 + 监控文件夹"
- **规范化结论**: Tauri 文件系统集成时：
  - 支持打开本地 .md 文件
  - 监控文件夹（fs watcher）
  - **双向同步：DB ↔ 本地文件**
  - 外部修改时触发冲突检测 UI
- **硬约束**: IndexedDB 为 primary source；本地文件为 derived/mirror（与 F-02 语义一致）。
- **落地点**: `TauriFileBridge` Spec（与 R-06 Spec 联动）。

### 决策 F-06 | Git 同步与 DB 迁移/灾难恢复的交互

- **来源**: T07-02 D + X-04 B + X-11 C（冲突裁决）
- **规范化结论**: **IndexedDB 为 primary source of truth；Git 为 derived mirror**：
  - Git push：从 IndexedDB 导出到 Git 仓库
  - Git pull：检测到 Git 仓库变化时走冲突解决 UI（F-03）
  - DB 迁移失败：进入安全模式，不主动触发 Git pull
  - DB 损坏：优先从版本历史恢复（E-07），其次才考虑 Git 恢复
- **硬约束**: 禁止 Git pull 直接覆盖 IndexedDB。
- **落地点**: Part 2 域 J Sync 架构图。
