## 总览：用户核心产品哲学

**第一段 — 产品定位**：
InkForge v2.1 的产品哲学是"**Markdown-first 的单人深度写作与多渠道出版中枢**"。核心交付场景是 **A（单人深度写作）+ D（多渠道高保真出版）双轴**，把 C（知识增强）作为近期目标，B（团队协作）明确放到远期。目标用户优先是**个人本地用户**（L1-02 A），但在本轮就要为"远期 5-10 人小团队 + 管理员/非作者角色"打好底座（多账户、同步、审计、权限）。

**第二段 — 编辑器气质**：
坚持 **Markdown 文本作为唯一权威源**（L1-05 A），但对"当前 HTML 持久化现实"采取 **D 策略**——不立刻切换权威模型，先强制为 HTML 定义更严格的导出/版本/搜索契约，并参考微信公众号、小红书编辑器的权威实践。非标准 Markdown 能力参考 **Typora 策略**（L1-07 C），所有元素必须**无损 round-trip**（L1-08 C + 补充"所有元素必须无损"）。编辑范式默认 **Typora 式混合编辑**（L1-10 B），模式切换时**所有状态（选区/撤销栈/版本/评论锚点）必须继承**（L1-11 C）。纸张式气质不可破坏，但允许用户在"过重工具栏 / 简化工具栏"之间选择，动效是欢迎的（L1-12 B + 补充）。

**第三段 — 交付哲学**：
**零空壳交付**（L1-04 D）—— 任何进入 scope 的能力都必须做成完整垂直切片，且高风险能力必须有恢复/校验/错误处理链路。**全范围审计 + 3 个月保留 + 可导出 + 用户可查看**（L1-34 A+B+C + 补充）。**C 级防呆**（L1-40 C）+ 设置高危险操作二次确认。**完全开源，全部开放扩展（D 级 SDK）**，但通过沙箱/权限声明保证扩展不作恶（L1-37 D + L1-38 C）。

## 不可违反的铁律（从 L1-01~L1-40 提炼）

1. **铁律 1 — Markdown 是唯一权威源**：渲染/预览/导出/发布皆从 Markdown 文本派生，任何平台适配不得反向污染编辑权威模型（L1-05 A + L1-30 D）。
2. **铁律 2 — 所有元素无损 round-trip**：Typora / Source / Preview / Export 之间必须保证所有元素无损往返（L1-08 C + 补充）。
3. **铁律 3 — 零空壳交付**：任何 scope 内能力必须完整垂直切片 + 恢复/校验/错误处理（L1-04 D）。
4. **铁律 4 — 纸张式气质不可破坏**：视觉/颜色/行距/字体基调冻结；任何新功能必须服从纸张式写作体验（L1-12 B）。
5. **铁律 5 — Typora 式编辑默认 + 状态全继承**：默认 Typora 混合编辑；模式切换时选区/撤销栈/版本点/评论锚点必须连续（L1-10 B + L1-11 C）。
6. **铁律 6 — 版本恢复必须走 diff/merge 双栏视图**：恢复版本不是直接覆盖，必须打开 diff/merge 让用户选择性恢复 + 所有状态跟随（L1-18 D）。
7. **铁律 7 — 自动保存失败必须用户完全可见 + 日志留痕**：失败重试一次，不可静默失败；本地恢复点强制创建；提供失败明细与应急导出（L1-19 D + 补充）。
8. **铁律 8 — Sync 在 v2.1 必须真实落地**：WebDAV / Git / 自有服务三项必须落地，不是"远期预留"（L1-20 D + 补充）。
9. **铁律 9 — 冲突一律由用户解决 + 审计日志**：冲突不能自动 last-write-wins，必须走三方合并，失败时强制人工决策并写入审计（L1-22 D + 补充）。
10. **铁律 10 — 账户即 Profile，多账户可并行打开**：每个账户独立数据库+文件根；支持多窗口并行；允许共享模板/导出预设/AI 配置（L1-23 D + L1-24 D）。
11. **铁律 11 — 引用与溯源强制三层区分**：原始事实 / 模型推断 / 用户手写必须可区分；显示位置可配，导出保留，发布可隐藏（L1-26 D + 补充）。
12. **铁律 12 — 命令系统必须四类分离**：编辑命令 / 系统命令 / AI 命令 / 发布命令各自成域，支持可组合工作流（L1-27 D + 补充）。
13. **铁律 13 — 各发布平台各自成渲染链路**：本地预览/HTML/PDF/微信/小红书/知乎不共享同一 pipeline，各平台独立渲染规则（L1-30 D + L1-31 C + 补充）。
14. **铁律 14 — 公式/Mermaid/代码高亮三端高度一致 + 必须有降级策略**：按各平台渲染规则适配，不允许"编辑器可用但导出坏"（L1-32 C + 补充）。
15. **铁律 15 — 性能 SLO 硬指标**：输入无延迟；保存 ≤ 1s；冲突检测 ≤ 10s；导出 ≤ 3min（L1-36 C + 补充）。

## A. 产品定位与交付边界

### L1-01 | 产品第一性目标

**问题概述**: InkForge 第一版要先赢在哪个核心场景，决定主轴是编辑器/知识增强/评论审阅/发布。

**选项**:
- A: 单人深度写作工具优先 —— 核心是 Markdown 编辑、版本恢复、导出发布
- B: 小团队协作写作优先 —— 核心是评论审阅、权限、同步冲突、审计
- C: 知识增强写作工作台优先 —— 核心是资料摄取、引用溯源、AI/命令增强
- D: 多渠道出版中枢优先 —— 核心是一次编辑、多平台高保真输出

**用户选择**: A+D

**用户补充**: "必须以A和D选项为核心，C选项为近期，B选项为远期。四个选项都是必须要完成的内容。"

**决策含义**:
- 本轮主轴双核：单人深度写作 + 多渠道发布；知识增强是近期次轴；团队协作是远期预留
- 所有 Task 的优先级必须围绕 A/D 锚定；B（评论/审阅）要有框架但不深入，C 要留结构化接入点

**关联任务**: 跨任务/L1 全局（影响所有 T01-T09）

## B. Markdown 权威模型与内容真相层

### L1-05 | 内容的唯一权威源

**问题概述**: 内部内容权威模型选什么。

**选项**:
- A: Markdown 文本是唯一权威源，编辑器/预览/导出都从 Markdown 派生
- B: 内部 AST/JSON 是权威源，Markdown 只是输入输出视图
- C: 双模型并存 —— AST/JSON 为主，Markdown 为受控副本，并定义一致性规则
- D: 不设统一权威模型，各模块按自身格式工作，靠转换适配

**用户选择**: A

**用户补充**: "以Markdown文本作为唯一权威源的核心是它支持html+css渲染，这是我们发布到平台的优先关键；同时方便后期AI集成使用"

**决策含义**:
- Markdown 文本是唯一权威源；所有派生（HTML、PDF、发布、搜索索引）都从 Markdown 生成
- 为 AI 集成和多平台发布奠定基础

**关联任务**: T01 Typora、T04 渲染、跨任务

### L1-06 | 当前 HTML 持久化的处理态度

**问题概述**: 如何处理当前代码事实上是 HTML 持久化。

**选项**:
- A: 接受 HTML 继续作为权威源，Markdown-first 只体现在编辑体验上
- B: 逐步迁移到 Markdown 或 JSON 权威模型，但允许过渡期并存
- C: 立刻切换到新的权威模型，并提供迁移策略
- D: 不切换权威模型，但强制为 HTML 定义更严格的导出/版本/搜索契约

**用户选择**: D

**用户补充**: "必须参考市面上优秀的微信公众号、小红书编辑器"

**决策含义**:
- 与 L1-05 存在张力：L1-05 说 Markdown 是唯一权威，L1-06 却说不切换权威模型——需在 PRD 阶段明确"Markdown 是表达权威，HTML 是运行时持久化权威"的双层定义
- 强制参考微信/小红书编辑器的导出/渲染契约

**关联任务**: T01 Typora、T04 渲染、T09 UI 打磨

### L1-07 | 非标准 Markdown 能力的态度

**问题概述**: 无法无损回写到标准 Markdown 的能力怎么处理。

**选项**:
- A: 一律禁止 —— 任何内容都必须可无损回写到标准 Markdown
- B: 允许增强语法，但必须有明确 fallback 文本表示
- C: 允许富文本专属能力，但要显式标记"不可移植/不可纯 Markdown 导出"
- D: 按文档级策略切换 —— 某些文档严格 Markdown，某些文档允许增强能力

**用户选择**: C

**用户补充**: "这里必须参考typora的策略"

**决策含义**:
- 允许 InkForge 专属增强（Callout、复杂 admonition 等），但必须显式标记可移植性
- Typora 的扩展语法（高亮、下划线等）是参考基准

**关联任务**: T01 Typora、T04 渲染

### L1-08 | Round-trip Fidelity 的最低要求

**问题概述**: 多模式之间的一致性门槛。

**选项**:
- A: 只保语义一致，不保源码细节
- B: 保常见 Markdown 结构与格式一致，复杂增强能力允许降级
- C: 保大多数 Markdown 与核心增强语法无损 round-trip
- D: 只要用户能看起来差不多即可，不强求严格 round-trip

**用户选择**: C

**用户补充**: "所有元素必须无损"

**决策含义**:
- 选项是 C，但补充把门槛拉到"所有元素无损"——实际要求高于 C 选项本身，接近 C+
- 任何增强语法在 Typora/Source/Preview/Export 四者间都必须往返无损

**关联任务**: T01 Typora、T04 渲染

## C. 编辑范式与纸张体验

### L1-15 | 评论锚点粒度

## 矛盾 / 模糊点清单

> 按重要性排序，建议在 PRD 阶段逐项澄清。

1. **L1-05 vs L1-06 — 权威模型定义张力**
   - L1-05 说"Markdown 是唯一权威源"，L1-06 却说"不切换权威模型（当前是 HTML 持久化）"
   - 建议解读：区分"**表达权威**（Markdown 源码是用户意图）"与"**运行时持久化权威**（HTML 可能仍是数据库层事实）"的双层定义，并定义两者间的一致性契约（写入时 Markdown → HTML 渲染缓存，读取时 Markdown 回写）

2. **L1-21 vs 补充 — 冲突粒度自相矛盾**
   - 选项选 D（不做多人并发，文档级假设），但补充说"我需要的是行内/标记级（C）"
   - 建议解读：**本轮代码架构按 D 走（单写者假设），但数据结构预留 C 级粒度**；远期升级时无须数据迁移

3. **L1-22 vs 补充 — 冲突解决策略自相矛盾**
   - 选项选 D（三方合并优先，失败才人工），但补充说"一律以用户解决为主（= C）"
   - 建议解读：**默认尝试三方合并，但即使成功也要让用户确认**；UI 始终显示三方合并结果让用户裁决

4. **L1-30 vs 补充 — 渲染链路是否共享自相矛盾**
   - 选项选 D（共享同一 canonical render pipeline + 不反向污染），但补充说"不可能共享，各平台独立链路"
   - 建议解读：**Markdown 权威源共享（所有平台都从同一源派生），但从 Markdown 到平台产物的转换管道互相独立**；"不反向污染"铁律保留

5. **L1-34 vs 补充 — 审计范围自相矛盾**
   - 选项选 A+B+C（明确排除 D 的 AI/命令留痕），但补充说"全范围审计"（含 D）
   - 建议解读：**PRD 按 D 落地**（所有 AI/命令也留痕），保留期 3 个月

6. **L1-28 未填写 — 命令系统权限与回滚**
   - 题目空白
   - 建议推断：参考 L1-34 + L1-40 倾向应选 **D**（所有改数据的命令都需确认+回滚点+权限约束+审计）

7. **L1-08 选项 vs 补充的强度差**
   - 选项 C（"大多数 Markdown 与核心增强语法无损"）但补充要求"所有元素必须无损"
   - 建议解读：实际执行门槛是 C+（接近 D 级但对富文本独占能力仍允许显式标注为非可移植）

8. **L1-25 D 级范围 vs 本轮 scope 可行性**
   - 选 D（云文档/代码仓/数据库/第三方知识库连接器）是非常重的承诺
   - 建议解读：v2.1 实现连接器 Provider 接口 + 至少本地 + URL 两个实现；云文档/代码仓为 stub 骨架

9. **L1-12 B 选项 vs 补充 — 工具栏重度化与纸张气质的张力**
   - 选 B（冻结纸张视觉但允许灵活改其他），补充说"允许过重工具栏，动效欢迎"
   - 与 L1-39 A 的"Typora/iA Writer 安静写作核心"方向存在张力
   - 建议解读：**"简化工具栏"为默认，"过重工具栏"为可切换模式**

10. **L1-20 Sync 承诺重度 vs 本轮工期**
    - 选 D 并要求"WebDAV + Git + 自有服务"必须落地
    - 建议解读：三种 Provider 接口全部 ready + 至少 WebDAV 和 Git 两个可用实现；自有服务可作为 MVP 级实现
