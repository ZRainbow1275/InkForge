# Long-form UX Review — 数字人民币战略报告 (WeChat 渲染)

**Verdict: WARN / CONCERNS** — pipeline is fundamentally sound and the rendered article is readable end-to-end, but four real frictions will degrade the WeChat reader's 100-minute journey: hierarchy collapse (部分 / 1.x 视觉同形), markdown 残留 (`**…**` 未转义, `<strong>` 嵌套破坏), zero navigation affordance for a 4-万字 piece, and an unused citation feature that quietly hides 7+ authority references (BIS / IMF / G20 / mBridge / Libra / GENIUS / 国务院). None are pipeline bugs in the strict sense, but together they shift the article from "professional report" to "long wall of identical-looking text."

## 1. Reading-time accuracy
Header at HTML line 33 reads `阅读约 100 分钟 · 全文 29919 字 · 1 张表`. Math is correct (29919÷300 cpm = 99.7, ceil = 100, `utils.ts:661`). **But 300 cpm is wrong for this audience**: native CN readers cruise at 500-600 cpm for narrative prose, 350-450 cpm for analytical/policy text. The article is policy-heavy but well-structured — realistic time is 70-85 min. Displaying "100 分钟" on a WeChat opener creates an immediate bounce risk; readers see "1 小时 40 分" and swipe away. **Recommendation**: expose `readingSpeed` per preset; `report` should default to 400 cpm, yielding ~75 min — still honest, less intimidating.

## 2. Opening hook
The lede (HTML line 35) "2025 年秋，上海数字人民币国际运营中心…" is strong copy but rendered as plain `<p>` identical to every other paragraph — same font-size 16px, same margin, no drop-cap, no lede emphasis, no leading-section visual anchor. The first 5 paragraphs all look identical until the `<hr>` at line 40. For a 100-min commitment, the opening needs **one moment of visual delight** to earn the swipe-down. The `<hr>` gradient bar at line 40 is the only graphic before the reader meets a wall of H3+paragraph. **Recommendation**: render the first paragraph at 1.05em with slightly tighter line-height (1.7) and an optional left-border accent in primary color, OR auto-detect "本报告…" sentence and wrap as a stylized abstract block.

## 3. Chapter rhythm — CRITICAL hierarchy collapse
Source markdown uses ONLY `###` for both `第一部分` (top-level) and `1.1 / 1.2 / 1.3` (sub-level). The renderer faithfully applies **the identical H3 style** (line 41 vs line 43): same `font-size:1.15em`, same `border-left:3px solid #004080`, same color. A reader scrolling at WeChat-speed cannot tell whether they just crossed a major part boundary or just moved from §1.3 to §1.4. With 6 parts × ~4 subsections = 24+ section transitions visually indistinguishable, the reader loses the report's spine. **Recommendation**: detect the `第X部分` pattern in the H3 transformer and apply a stronger visual treatment — larger font (1.35em), full-width top border, top-margin 3em, or a section-counter badge. Currently 5 of 6 part headings are reachable but invisible (HTML lines 41, 139, 330, 408 + part 三/四 between).

## 4. Reader checkpoints
For 100 min on mobile, healthy rhythm = visual rest every 8-12 min (~3000 字 → ~5 scroll-screens). The article has **only 1 `<hr>`** (line 40 — the opening separator before §1) and **10 strong checkpoint markers** ("阶段性结论"×2 at line 168, "结论：" at lines 200/202/257/403/419, "核心发现"×3 at lines 410/412). That's actually decent semantic content, but the markers are rendered as plain `<strong>` inline text — **they don't form visible rest stops**. There is no TOC, no progress indicator, no chapter-back-to-top, no "本节小结" callout. **Recommendation**: inject an `<hr>` automatically before every `第X部分` H3, and detect "结论：/小结/核心发现" prefixes to wrap the surrounding paragraph in a tinted callout block (reuse the alert-block infrastructure at `utils.ts:490`).

## 5. Footnote-vs-inline citation — content gap, not pipeline gap
Stats confirm `linkCount: 0`. The article cites BIS, IMF, G20, mBridge, Project Ensemble (16 matches across the rendered HTML for these terms), 《中国人民银行法》, Libra 白皮书, GENIUS法案, 国务院, 央行行长潘功胜 — all as **inline plaintext name-drops with zero verifiable source**. The cite-status pipeline (`convertLinksToFootnotes` at `utils.ts:586`) is wired correctly and would have produced a footnote section had source `<a>` tags existed. So the failure is upstream: **the source markdown was authored without hyperlinks for an academic-leaning piece**. From a reader-trust perspective on a policy report, this is the single biggest credibility leak. **Recommendation**: either author-side discipline (add links in markdown), or pipeline-side enhancement — detect institution name patterns (BIS/IMF/G20/Libra) and auto-attach a `[资料来源待补]` superscript so the reader at least knows references are intended.

## 6. Conclusion / call-to-action
Section 6.2 (HTML lines 419-423) addresses 政策制定者 / 金融机构 / 企业 — the three audience pillars. **Two problems visible**: (a) line 420 contains broken markdown `**…**<strong>…</strong>` interleavings — see `立法铸基<strong>...` and `“中国方案”**` at line 420, also line 422 has `**“效率红利”<strong>…</strong>“商业模式革命”**` — the `**` markers leaked through because nested `**xxx**` inside already-bolded segments confused the markdown parser. This affects the most-quoted-from section of any report (the action-plan). (b) Each audience pillar should be a visually distinct block; currently all three render as identical paragraphs starting with bolded keyword. **Recommendation**: fix the markdown-bold collision first (this also affects HTML lines 47, 54, 420, 422 — at minimum 4 paragraphs), then consider rendering audience-callouts as a 3-column or 3-card block at the conclusion.

## 7. Total payload feel
172KB HTML for 100-min article. Typical mobile WeChat long-form is 50-80KB; this is **~2× bloated**. Cause is inline-style verbosity: every `<strong>` carries `style="color:#004080;font-weight:700;background:linear-gradient(180deg, transparent 60%, rgba(0,64,128,0.15) 60%);padding:0 0.1em"` (177 bytes per strong) — and the article has 200+ strong elements, contributing ~35KB just for repeated highlight styling. Every `<p>` carries 130 bytes of redundant style. On 3G mobile this adds 1-2s to load. **Recommendation (out of scope for this fix but worth flagging)**: the WeChat copy-flow injects a single `<section id="nice">` with shared styles, but `juice` inlines everything. A post-juice de-duplication of identical-prefix styles via CSS variables would cut payload ~30%. Acceptable for now since WeChat's editor accepts 172KB without complaint, but for a 4-万字 piece it crosses a perceptible threshold.

---

## Top 3 actionable fixes (impact-ordered)

1. **Fix nested-bold markdown collision** — broken `**` leaks visible in conclusion §6.2 (lines 420, 422) and intro §1.1 (lines 47, 54). This is the only **content-correctness** bug; everything else is UX polish. The most-quoted "action plan" section currently shows literal asterisks.
2. **Distinguish 第X部分 H3 from 1.x H3** — biggest navigation win for the reader. Same HTML transformer can emit two style tiers based on regex match on the heading text. Without this, the 6 major part boundaries are invisible and the 100-min read feels like one undifferentiated wall.
3. **Right-size the reading-time** — `readingTime: 100` is mathematically defensible but psychologically a bounce trigger. Bump `report` preset's `readingSpeed` to 400 cpm (still conservative for policy text) → displays "75 分钟", which earns the swipe-down. One-line change in preset config.
